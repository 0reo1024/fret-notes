# Fret Notes デスクトップ改築方針

作成日: 2026-10-12
状態: 改築の基準となる方針。2026-10-13に第4段階の単音演奏練習まで実装した（0.4.0）。ギターの一部の実入力と解析イベントによる判定を確認し、一連の実演奏・ベース・切断等の実機評価は継続課題。実装済み・未検証・後続機能の区別は [移行の進捗](migration-progress.md) を参照。

## 1. 到達点

Windowsで専用ウィンドウを持つFret Notesを起動し、指板の学習、任意チューニング、単音チューナー、指定音を弾く練習をオフラインで利用できるようにする。

採用する軸は **Tauri 2 + TypeScript + Rust**。画面にはHTML/CSS/SVGとWebView2を使う。配布版はアプリに画面を内包し、利用者がNode.jsやローカルHTTPサーバーを起動する必要をなくす。開発時はNode.js/Viteを利用する。

軽さは配布容量だけでなく、起動時間、アプリ全プロセスのメモリー、待機時CPU、音声入力中のCPU、検出遅延で評価する。言語の置き換えだけを性能改善とは扱わない。

## 2. 現状と引き継ぐもの

現状はフレームワークなしのHTML/CSS/JavaScript。`scripts/server.mjs` が `dist/` を配信し、設定はlocalStorageに保存している。

| 現在のファイル | 改築先・扱い |
| --- | --- |
| `dist/core.js` | 指板計算・出題・回答判定をTypeScriptの独立モジュールへ移す |
| `dist/theory.js` | 音名、度数、コード、スケールをTypeScriptへ移す |
| `dist/shapes.js` | シェイプの定義・検証を分離し、チューニングの適用条件を持たせる |
| `dist/app.js` | 画面、練習状態、保存処理、楽器切り替えを分割する |
| `dist/index.html` / `dist/bass.html` | 楽器設定に基づく単一のアプリ画面へ統合する |
| `dist/style.css` | 現在の配色・視認性を引き継ぎ、部品単位に整理する |
| `tests/*.test.cjs` | 既存仕様の回帰テストとして引き継ぎ、移行後のモジュールへ接続する |

既存の3学習モード、ギター・4弦/5弦ベース、19コード・21スケール、4層比較、音の度数確認、標準チューニングのシェイプ、出題範囲設定、キーボード操作を移行対象にする。

現在の指板計算は音を12種類の音高クラスとして扱う。演奏入力にはオクターブが必要なため、絶対音高を追加する。現在の弦番号、異名同音の表記、重複しない出題、既存の位置回答ルールは明示的にテストして移行する。

## 3. 役割の分担

| 層 | 担当 | 設計規則 |
| --- | --- | --- |
| UI / TypeScript | 指板、出題、チューナー、設定、結果表示 | 音声サンプル処理や直接のファイル書き込みを持たない |
| 学習・音楽理論 / TypeScript | 音名、度数、指板、出題、練習セッション、回答判定 | DOM・Tauri・保存方式に依存しない純粋な処理にする |
| 接続層 / TypeScript | Rustへの要求と結果の受け渡し | 画面各所から直接Tauriを呼ばず、型のある窓口へ集約する |
| アプリ本体 / Rust | ウィンドウ、保存、音声デバイス、音声処理の開始・停止 | UIからの入力を検証し、失敗を状態として返す |
| 音声エンジン / Rust | 入力、音高推定、音の立ち上がり、将来のメトロノーム | UIの更新周期に依存せず、時計とバッファを管理する |
| 保存 / Rust | 設定JSON、将来の練習履歴SQLite | スキーマの版番号、移行、復旧を管理する |

画面はまずTypeScriptとDOM/SVGの部品で構成し、Viteでビルドする。全体を巨大な文字列で毎回再描画する構造をやめ、指板・比較パネル・チューナーメーター等を必要な単位で更新する。特定のUIライブラリを使わなくても、部品と状態と音楽理論の境界を保つ。

通常の操作はTauri command、継続する音高・入力レベル通知はchannelを使う。送受信するデータの型を定義し、Rust側で検証する。音声バッファはRust内に留め、UIへは表示に必要な解析結果だけを渡す。

### 予定するディレクトリ

```text
src/
  app/                    # 起動、画面の切り替え、依存の組み立て
  domain/
    music/                # 音高、音名、度数、コード、スケール
    instruments/          # 弦、チューニング、指板、シェイプ
    practice/             # 出題、回答判定、セッション状態
  features/
    fretboard-study/
    tuner/
    playing-practice/
    settings/
  ui/                     # 共通の画面部品、スタイル
  platform/               # Tauri通信、保存・音声サービスへの接続
src-tauri/
  src/
    commands/
    audio/                # デバイス、入力、解析、解析結果通知
    storage/              # 設定、データ移行

tests/

  integration/
  audio-fixtures/         # 条件の明らかなテスト信号・使用許諾済み録音

```

移行開始時に現行版の復元可能なGit履歴を確保する。新しい構成が検証できるまでは現行版を比較基準にする。移行後の`dist/`は生成物とし、編集するソースは`src/`へ移す。

## 4. 楽器・チューニング・練習の共通モデル

- `InstrumentProfile`: ID、表示名、弦ごとのIDと番号、開放弦のMIDI音高、フレット数、選択中チューニング。
- `TuningPreset`: ID、対応する弦構成、弦ごとの絶対音高。標準、Drop D、半音下げ、ユーザー定義を保存できる。
- `Pitch`: MIDI音高・周波数・オクターブと、表示用の音名を分ける。指板計算には絶対音高、コード判定や表記には必要に応じて音高クラスを使う。
- `PracticeSession`: モード、範囲、出題順、現在の課題、回答状態、結果。乱数と時計を差し替えて再現可能にする。
- `PitchObservation`: セッションID、単調増加の音声時刻、周波数、入力レベル、信頼度、安定/無音/不確実の状態。
- `PracticeTarget`: 目標音高、オクターブ一致の要否、許容セント幅、必要な安定時間。将来は演奏時刻も追加する。

配列の順番と画面上の上下を混同しないよう、弦番号を明示する。ギターは1弦E4〜6弦E2、4弦ベースは1弦G2〜4弦E1、5弦ベースは5弦B0を含む設定を検証する。

楽器・チューニング変更は指板、出題、チューナー目標音に一括適用し、進行中の課題を再生成する。標準用のコードシェイプを別チューニングにそのまま表示しない。シェイプはチューニングIDにひも付け、未対応時はその旨を表示する。任意チューニング用の運指生成は後続機能とする。

**入力音だけで弦・フレットの位置を断定しない。** 通常のマイク/単一入力では、異なる弦で弾いた同じ高さの音を確実に区別できない。演奏練習は音高を採点し、推奨する弦・位置はガイドとして表示する。既存のクリックで位置を選ぶ練習の判定とは分ける。

## 5. 音声処理とチューナー

音声I/OはRustのCPALを第一候補にして、Windowsの標準入力経路で検証する。入力デバイス・チャンネル・対応サンプルレートを取得し、USBオーディオインターフェースとマイクを選べるようにする。機器互換性は実機確認を必要とし、ASIO対応は別の検証課題とする。

処理の流れ:

```text
入力デバイス
  → 音声コールバック → 容量を固定したバッファ
  → 解析スレッド（入力レベル、音高、信頼度、時刻）
  → 通知用の処理 → Tauri channel
  → TypeScriptの練習状態・チューナー表示
```

音声コールバックではファイル保存、UI通知、待ち合わせ、重い解析を行わない。入力データを渡す処理に限定し、バッファあふれを検知できるようにする。UIの更新通知はまとめ、処理が追いつかない場合も通知キューを無制限に増やさない。

単音の音高推定はYIN系などを試作候補とし、ギター・ベースの実録音で比較して選定する。低いB0/E1は解析に必要な時間と表示の反応速度が両立するかを早期に確認する。倍音を基音と誤認するケース、アタック、減衰、弦の共鳴、入力飽和、環境音を検証対象にする。

チューナーはクロマチック表示と選択弦の目標表示を用意する。A4=440 Hzを初期値とし、基準周波数を変更できるようにする。周波数、音名、セント差、入力レベルを表示し、無音・不確実な音では直前の値を正しい検出のように出し続けない。

入力開始はユーザー操作で行い、利用中の状態と停止操作を表示する。入力権限拒否、デバイス未接続、使用中、抜き差し、スリープ復帰を扱う。チューナーと練習は音声エンジンを共用し、二重に入力を開かない。不要時・終了時には確実に停止する。

## 6. 演奏練習の初期仕様と拡張順

初期版は「指定された単音を弾く」。指板位置/音名を出題し、入力音が許容範囲内で一定時間安定したときに正解とする。単一フレームの一致だけで進めない。正解後は離音または次のアタックを待つなどして、伸ばした同じ音を次の問題にも連続加点しない。

状態は `ready → listening → candidate → accepted → awaiting-next` を基本とし、一時停止、停止、入力エラーを明示する。UIから独立させ、記録済みの音高イベントで正誤判定を再現できるようにする。

拡張の順序:

1. 指定された単音を弾く。
2. スケール/アルペジオを順番に弾く。
3. メトロノームに合わせて音とタイミングを判定する。
4. フレーズ練習、履歴、苦手区間の復習。
5. 複数音のコード認識は、単音判定の精度とは別に調査・評価する。

将来のタイミング判定はRustの音声時刻を基準にする。画面のタイマーや通知到着時刻で採点しない。入力遅延の補正、アタック時刻の推定、メトロノーム出力との時計の対応を検証する。

## 7. 保存と旧設定の移行

初期版はTauriのアプリデータ領域に、版番号付きJSONで設定を保存する。画面サイズ、楽器別の練習範囲、チューニング、音声デバイス設定を対象にする。Rust側の窓口で入力を検証し、一時ファイルを用いた更新と直前の正常データによる復旧を実装する。

旧ブラウザーのlocalStorageはデスクトップ版から直接引き継げない。必要な既存設定は旧ローカル版にJSONエクスポート、新版にインポートを用意して移す。未取得のWork版ブラウザー設定が自動移行されたとは扱わない。

練習履歴を導入する段階でSQLiteを追加し、スキーマ移行とセッション単位のトランザクションを用意する。単純な設定のためだけにDBを先行導入しない。音声は初期版では解析のみとし、録音ファイルの保存は別の利用者操作として設計する。

## 8. 実装段階と完了条件

| 段階 | 実装内容 | 完了条件 |
| --- | --- | --- |
| 0: 基準と実現性 | 現行版の保全、既存テスト・画面仕様の記録、Tauri最小ビルド、Rust音声入力/低音解析の小さな試作 | このPCで専用ウィンドウが起動し、音声入力の互換性・低音検出の問題点を把握できる |
| 1: デスクトップ基盤 | Tauri/Vite/TypeScript構成、音楽理論と画面の分離、既存3モード、保存窓口、旧設定の入出力 | 既存テストと操作確認が通り、サーバーを手動起動せずexeで使える。設定が再起動後に復元する |
| 2: 楽器・チューニング | オクターブ付き音高、共通InstrumentProfile、プリセットとユーザー定義 | チューニング変更が指板・出題に反映し、標準の既存表示を維持する。未対応シェイプを誤表示しない |
| 3: チューナー | デバイス選択、解析、音名/セント表示、基準周波数、入力状態管理 | 合成信号と実録音で精度・反応時間を評価し、実機でギター/ベースの入力を確認する。切断・無音でも誤った成功表示をしない |
| 4: 単音の演奏練習 | 目標音、安定判定、問題の進行、一時停止、結果表示 | 正解・不正解・オクターブ違い・伸ばした音・再アタックを再現テストでき、実際に弾いて一連の練習ができる |
| 5: 配布と性能調整 | Releaseビルド、インストーラー、測定、終了/再起動/保存検証 | 開発サーバー停止中に配布物から起動でき、必要なWebView2の扱いが明確。性能測定結果と残る実機制限を記録する |

最初の完成版の範囲は段階5まで。各段階で動く成果物を確認し、音声試作で互換性や精度に問題が見つかった場合は、広い機能追加より先に方式を修正する。

## 9. 検証と軽さの判断

- 音楽理論: 既存の19コード/21スケール、680のルート組み合わせ、2,799シェイプ等の検証を引き継ぐ。オクターブ、任意チューニング、異名同音を追加する。
- 音声解析: 既知周波数の信号、倍音を含む信号、ノイズ、無音、入力飽和、音の切り替わりを検証し、音高誤差・オクターブ誤検出率・安定までの時間を記録する。
- 実機: ギター低音E2、4弦ベースE1、5弦ベースB0を含む音域を確認する。利用できる楽器/機器がない項目は未検証として残し、合成信号だけで実機対応済みとしない。
- 演奏判定: 同じ音の連続出題、長いサステイン、無音、早い音の切り替え、遅れて到着した前セッションの通知を確認する。
- 保存: 不正/古いJSON、書き込み失敗、復旧、旧設定インポート、再起動後の復元を確認する。
- UI: 楽器切り替え、3学習モード、比較表示、シェイプ、キーボード、ウィンドウ縮小とWindows表示倍率を確認する。
- 性能: Releaseビルドで、起動から操作可能まで、プロセス全体のメモリー、待機時/解析時CPU、解析から表示までの時間、配布容量を記録する。初回起動と通常起動を分ける。

許容誤差、安定時間、通知周期などは設定値として分離する。段階0の測定で初期の数値目標を決め、低音と高音・マイクと直接入力を区別して評価する。測定前のメモリー量や遅延を達成済みの数値として約束しない。

## 10. 現在の開発環境と次の着手点

このPCでNode.js/ViteとRust MSVCのビルド、WebView2による専用ウィンドウの起動を確認した。単音演奏練習を0.4.0へ追加し、設定はschemaVersion=3を維持する。

次は第5段階の配布と性能調整。起動・待機/解析時CPU・アプリ全体のメモリーを測定し、インストーラーとWebView2の扱いを整える。実機再接続は利用者の希望により後日行い、最終推定器の実音精度、ベース低音、切断/復帰、専用画面で一連の演奏練習ができることを継続評価する。Windows優先、既存機能の互換性重視、単音入力を初期対象とする。クロスプラットフォーム配布、ASIO、リアルタイム音声エフェクト、コードの同時発音認識は、それぞれ必要になった段階で追加評価する。
