# Part 5：開発ロードマップ

## 5.1 依存関係

```text
P0 実機ベースライン ──────────────────────────────┐（音声判定に関わる全工程の前提データ）
P1 和声エンジン ─┬─> P5 コードトーン ─> P6 インターバル・アルペジオ
                 │                         │
P2 判定の一般化 ─┼─> P4 指板拡張            │
 ＋音声ハブ      │                         ▼
P3 記録ストア ───┴─> （P4以降の全トレーナーが記録を書く）
                         P7 進行（ステップ式） ─> P8 メトロノーム＋自動進行 ─> P9 ボイスリーディング
                                                  │
                                                  ├─> P10 聴音（音の再生を使う）
                                                  ├─> P11 リズム（タップ）─> P12 オンセット検出＋演奏リズム
                                                  └─> P13 モチーフ・フレーズ
                         P14 上級ハーモニー（P5・P7・P9の上に）
                         P15 学習管理の高度化（P3の上に、データが溜まってから）
```

- 依頼の優先順位（指板 → 3rd/7th → インターバル → 進行・ボイスリーディング → 聴音・リズム → 上級 → 学習管理）は、ほぼそのまま保っている。
- 変更点は、共通基盤（P1〜P3）を先に小さく作ったこと。こうすると、P4以降のどのトレーナーも、作った時点から記録と演奏判定を使える。
- P1〜P3 はそれぞれ数日規模の作業で、P4・P5 から実際に使える機能が増える。

## 5.3 各フェーズで共通の完了手順

1. `npm.cmd test`、`npm.cmd run typecheck`、`cargo test --manifest-path src-tauri/Cargo.toml --lib` がすべて成功する。既存のテストは削除しない。変更が必要な場合は、理由を書いたうえで仕様を保ったまま書き換える。
2. 開発プレビュー（`.claude/launch.json` の `web`）で、新しい画面と既存の3機能（指板学習、チューナー、演奏練習）を操作して確認する。音声入力はプレビューでは使えないため、音声の判定はフィクスチャのテストと、必要に応じて実機で確認する。
3. `docs/migration-progress.md` に、版・実装した内容・検証した内容・**未検証の内容**を追記する。README の「現在使える機能」を更新する。
4. 版を上げる場合は、`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` を揃える。`installer/fret-notes.iss` の AppId は変更しない。
5. 最後に `npm.cmd run desktop:install` を実行する。
