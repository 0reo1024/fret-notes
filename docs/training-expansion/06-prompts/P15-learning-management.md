# P15 学習管理の高度化（弱点分析・レベル・今日の練習・出題の重み付け）

あなたは Fret Notes（Tauri 2 + TypeScript + Rust）の開発を担当します。今回は、P3 で作った学習記録を使って、弱点の可視化、レベル（到達）の判定、間隔反復による出題の重み付け、「今日の練習」の自動メニューを実装します。

## 目的
- 仕様は `docs/training-expansion/03-feature-specs.md` の §3.11、`04-architecture.md` の §4.4 と §4.6.1、`07-proposals.md` の P-5。
- 短期的に正解できること（今回の正答率）と、長期的に定着していること（間隔反復の箱、異なる日の正解、反応時間）を区別して見せる。

## 最初に確認すること（既存コード）
- P3 の `src/domain/training/records.ts`（`review`、`record`、`isMastered`）と `TrainingRepository`、記録タブ。
- 各トレーナーの項目IDの形式（`fb:`、`note:`、`ct:`、`iv:`、`ivf:`、`arp:`、`key:`、`chg:`、`ear:`、`rhy:`、`play:`）と、実際に記録されている層（knowledge / fretboard / performance）。
- 各トレーナーの出題デッキの生成（P4〜P14）。重み付けを差し込める箇所。
- 記録データの実際の大きさ（数百件の試行を記録した状態で確認する）。

## 変更対象と要件
1. ドメイン（新規・提案名 `src/domain/training/analysis.ts`）
   - `weakness(stats, filter)`: 項目を交差表に集計する。
     - 品質 × 度数（ct）
     - インターバル × 方向（iv）
     - 弦 × フレット帯（fb）
     - 音数 × 種類（ear）
     - パターン × テンポ帯（rhy）
     - 各セルの値: 試行数、正答率、反応時間の中央値、定着の割合。
     - 試行数が少ないセル（5回未満）は「データ不足」とする。
   - `levelProgress(stats, level)`: §4.6.1 の各レベルの項目の集合と、定着の割合（80%で到達）。
   - `weightedDeck(items, stats, now, random)`: 優先順位は次のとおり。
     1. 期限が来た項目
     2. 弱点（正答率が低い、反応時間が長い）
     3. 新しい項目
     4. 定着した項目（低い頻度）
     - 一巡するまで重複させない規則を保つ。同じ項目を連続させない。
   - `todayMenu(stats, now)`: 復習（5分）→ 弱点（5分）→ 新しい項目（3分）→ 進行・フレーズ（5分）。対象の項目がない段階は省く。
2. 各トレーナーへの組み込み
   - 出題の設定に「苦手を優先」（オン／オフ。既定はオン）を追加し、`weightedDeck` を使う。オフにすると今までのランダムな一巡になる。
   - **既存の指板学習（位置→音名など）の既定の挙動は変えない。** 苦手を優先するのはオプションにする。
3. 記録タブ
   - 概要: 今日と今週の練習時間・問題数・正答率、連続練習日数。
   - レベル: L1〜L7 の進み具合のバー。到達したレベルの日付。
   - 弱点: 交差表を色で示す（色だけに頼らず、数値と記号も表示する）。セルを選ぶと「苦手を練習」ボタンでそのトレーナーへ移り、その項目だけを出題する。
   - 「今日の練習」: メニューを表示し、順に各タブへ移る。終わったら記録タブへ戻る。
   - 入力の状態: `detection-issue` の割合が高い場合に、入力レベルや無音のしきい値の見直しを案内する（チューナーの画面へのリンク）。
   - 書き出し・読み込み・消去（P3 のものを使う）。
4. 定着の基準の設定
   - 目標の反応時間を、回答方法ごとに設定できるようにする（既定: 選択 2.5 秒、入力 3 秒、クリック 3 秒、演奏 4 秒）。
   - 変更は今後の判定にだけ適用する（過去の箱を計算し直さない）。

## UI・UX 要件
- 記録タブは「次に何をすればよいか」が一目で分かるようにする（今日の練習を最上部に置く）。
- 数値の羅列を避け、交差表は最大でも 12×7 程度に収める。

## 音声認識との連携要件
- `detection-issue`、`skipped`、`self-marked` は弱点の計算と箱の昇降に使わない（P3 の規則を守る）。入力の状態の欄だけに集計する。

## テスト
- `weakness`: 集計、データ不足、層の分離。
- `levelProgress`: 境界（79%、80%）。
- `weightedDeck`: 期限が来た項目が先に出る、同じ項目が連続しない、一巡で全項目が出る、オフのときに従来の挙動と同じ。
- `todayMenu`: 空のデータ、期限の項目だけ、全種類。
- 大きな記録（2,000試行、3,000項目）での集計時間が、画面の操作を妨げない程度（例: 50 ms 未満）。

## 完成条件
- §3.11 の受け入れ条件。全テストが成功する。版は 1.0.0 にする。ただし、総合的な実機評価（ギター・ベース、全トレーナー）の結果と未検証の項目を `migration-progress.md` に記録する。

## 共通ルール（必ず守ること）
- 作業前に CLAUDE.md、docs/training-expansion/ の該当節、docs/migration-progress.md を読む。仕様と実際のコードが食い違う場合は、コードを確認したうえで食い違いを報告し、既存の挙動を壊さない側を選ぶ。
- 既存の機能を削除・変更しない（このプロンプトで明示した変更を除く）。既存のテストを削除しない。
- 新しいライブラリ・外部API・クラウドサービスを追加しない。src-tauri/tauri.conf.json の CSP（connect-src）を広げない。
- 音声データを保存・送信しない。テスト用のフィクスチャは解析結果（時刻・状態・周波数・レベル）だけにする。
- 音楽理論と判定のロジックは、DOM に依存しない src/domain/ に置き、tests/*.test.ts（node --test、tsx）で表を使ったテストを書く。
- ギター、4弦／5弦ベース、任意チューニングのすべてで動くようにする。単音認識しかできない前提を守り、和音認識を前提にしない。
- 新しいファイルの書き方は src/domain/practice/performance.ts に合わせる。既存ファイルを整形し直さない。不必要な大規模リファクタリングをしない。
- 完了時:
  1) npm.cmd test、npm.cmd run typecheck、cargo test --manifest-path src-tauri/Cargo.toml --lib をすべて成功させる。
  2) 開発プレビュー（.claude/launch.json の web）で、新機能と既存の3機能（指板学習・チューナー・演奏練習）を操作して確認する。
  3) docs/migration-progress.md と README.md を更新する。実装したこと、検証したこと、未検証のことを分けて書く。
  4) 版を上げる場合は package.json、src-tauri/tauri.conf.json、src-tauri/Cargo.toml を揃える。installer/fret-notes.iss の AppId は変更しない。
  5) 最後に npm.cmd run desktop:install を実行する。
- git のコミット・プッシュは、利用者の指示があるまで行わない。
