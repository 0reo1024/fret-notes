# Part 7：追加の提案

## 7.1 学習方法の提案

### P-1 「歌ってから弾く」（オーディエーション）

- **内容**: コードトーン・聴音・ラインの各練習に「先に歌う」オプションを付ける。手順は次のとおり。
  1. 出題（例: G7 の 3rd）を見たら、まず歌う。
  2. マイクで音高クラスを判定する（±50セント、半音単位）。
  3. 続けてギターで弾く。
- **理由**
  - 依頼の目標8（頭の中のメロディを弾く）は、「頭の中で正しい音を鳴らす」ことと「それを指板に写す」ことの2段階に分けられる。
  - 歌唱は前者を直接鍛える。Guthrie Govan や多くのジャズ教育者も、歌いながら弾くことを推奨している。
  - 既存の YIN（25〜1500 Hz）で人の声を検出できる。
- **注意点**
  - ギターをライン入力でつなぐ場合、声を拾うには別のマイクと入力チャンネルが必要になる。そのため、モードごとに入力チャンネルを選べるようにする（音声設定の部品を使う）。
  - 歌う声域はオクターブがずれやすいため、判定は音高クラスに限る。

### P-2 ターゲットノートの着地（進行トレーナーの段階7に組み込み済み）

- 自由な即興を採点しない。そのうえで「コードの変わり目に何の度数へ着地したか」だけを示す。
- 音楽性を損なわずに、理論が演奏に表れているかを確認できる。

### P-3 制約付き即興カード

- 「3音だけ」「1本の弦だけ」「休符で始める」「8分音符だけ」「各小節の頭は 3rd」といった制約を1枚ずつ出す。録音はせず、自己評価する。
- 自由すぎる即興は手癖に戻りやすい。制約を付けることで、新しい語彙を強制的に使わせる。

### P-4 ドローン上のモード練習

- ルートの持続音（＋5度）を鳴らし、その上でモードを弾いて、特性音（ドリアンの ♮6、リディアンの ♯4、ミクソリディアンの ♭7）の響きを覚える。
- 指板学習の「スケール表示」と組み合わせ、表示した音をドローンの上で鳴らせるようにする。
- 実装は P10 の合成音で十分にできる。

### P-5 「今日の練習」の自動メニュー（P15）

- 例: 復習が必要な項目 5分 → 弱点 5分 → 新しい項目 3分 → 進行の練習 5分。
- 間隔反復を、利用者が意識しなくても回せるようにする。

### P-6 ベースのウォーキングの骨格

- 進行に合わせ、1拍目にルート、3拍目に 3rd または 5th を弾き、4拍目に次のルートへの半音アプローチを入れる。
- 自動進行の判定に、拍ごとの条件を加えるだけで実現できる。ベース利用者にとって最も実用的な練習。

### P-7 演奏の「記録」は音高と時刻だけで残す

- 録音（音声ファイル）の代わりに、音のイベント（音高・時刻）を保存し、合成音で再生する。
- 利点
  - プライバシーの懸念がない。
  - 保存容量が小さい。
  - 音名や度数を表示できる。
- 実際の録音が必要になった場合は、後の段階で、オプトインで追加する。
  - 保存先はローカルだけ。
  - 保存期間と削除の操作を明示する。
  - Rust 側で WAV を書く。

## 7.2 構成についての提案

### 7.2.1 演奏練習と指板学習の統合（将来・要判断）

- 現在の「演奏練習」は、指板学習の「音名→位置」と同じ問いを「演奏で答える」ものにあたる。新しいトレーナーでは回答方法を共通の設定にしたので、将来は「指板学習 ＞ 回答方法: 演奏」に統合できる。そうするとタブが1つ減る。
- ただし、既存の機能を変えることになる。**利用者が判断するまで現状を維持する**（P4 では演奏練習を拡張するだけにする）。

### 7.2.2 15F以上への指板拡張（将来）

- 即興では、12F以上のポジションも実際に使う。ただし音名の学習としては、0〜12Fで全弦・全音高クラスを網羅できる。
- 拡張するには、次の箇所を同時に直す必要がある。
  - レイアウト（`fretboard-layout.ts`）
  - 範囲UI（`range.ts`）
  - `board.ts` と `performance/view.ts` のループ
  - `profiles.ts` の `fretCount`
  - Rust の `PlaySettings::validate`（`frets ≤ 12`）
  - シェイプの上限（15）
- 範囲が広いため、専用のプロンプトとして独立させる。
- 拡張してもギターの最高音は約 E6（1319 Hz）で、解析範囲の上限（1500 Hz）に収まる。

### 7.2.3 スマートフォン・タブレット

- 現在は Windows のデスクトップ版だけ。
- Tauri 2 はモバイルに対応しているが、次の確認が必要になる。
  - CPAL（Android / iOS）での入力
  - 権限
  - 遅延
  - タッチ前提のUI
- 依頼の UI 条件（スマホ・タブレットでも使いやすい）は、「狭い幅とタッチでも破綻しない設計」として各機能の仕様に反映した。**実際の移植は、別のプロジェクトとして判断する**ことを提案する。

### 7.2.4 同梱する進行と著作権

- コード進行そのもの（ii–V–I、ブルース、循環など）は一般的な型として同梱できる。
- 特定の曲のメロディや歌詞は同梱しない。
- 曲の進行は、利用者が自分で入力して保存する方式にする（§3.5）。

## 7.3 設計上の判断の要約（なぜこの構成か）

| 判断 | 理由 |
| --- | --- |
| A・B・C を1画面・1エンジンにまとめた | 問いの形が同じで、回答方法4種類を1回の実装で済ませられる |
| 知識・指板・演奏を別々の統計にした | 依頼の §9 の段階（認識 → 発見 → 演奏）を測るため |
| 自動進行の判定窓を広くした | 検出の遅延（0.2〜0.45 秒）があっても、正しい演奏を不正解にしないため |
| リズムをタップから始めた | 現在のエンジンでは発音の時刻を取れない。タップなら今すぐ客観的に測れる |
| モチーフを採点しない | 音楽的な正解は複数あり、点数にすると学習を歪めるため |
| 学習記録を別ファイルにした | 設定の厳格なスキーマと64KBの上限を避け、既存の設定を壊す危険をなくすため |
